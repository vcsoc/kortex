## Rooted-reader performance continuation: EARLY additive contract

**IMPLEMENTED / scoped validation complete; parent acceptance pending.** This exact additive API was published before consumer integration and is now available. Application/indexer may plan against `kortex_repo::ConfinedReader::new(root: &Path) -> Result<Self>`, `read_bytes(&mut self, relative: &str, max: u64, control: &RequestControl) -> Result<Vec<u8>>`, `read(&mut self, relative: &str, max: u64, control: &RequestControl) -> Result<String>`, and `stats(&self) -> &ConfinedReadStats`. Root must already be canonical/trusted at initial acquisition. The reader holds a source capability, NOT a private derived-data DirectoryAnchor. It accepts readable shared source directories and never alters modes/ACLs. Counters report actual root/parent/file opens, path checks, canonicalizations, read calls and bytes; no source names/contents are logged.

`discover`/`discover_with_control` now use one such reader per complete discovery; old standalone APIs remain compatible. Every source is actually read and hashed. Unix parent reuse is bounded to one at-most-32-component chain, checked descriptor-relatively from the held root before AND after each read; changed identities are refused, never blindly reused. Deeper paths use uncached descriptor walks and identity comparisons. Windows reuses one cap-std capability, preserves existing reparse/device/stream restrictions and remains unexecuted here. No ambient read fallback. Root spelling is rechecked against the held identity around reads; initial ancestors remain trusted, and these checks do not prove an atomic filesystem snapshot or defeat arbitrary ABA/same-UID attacks. Experimental stamps remain rehashing and separate.

### Exact behavior / integration

- `ConfinedReader` holds one canonical source root; Unix retains at most one 32-parent chain, truncating at the common prefix when visiting another path. Each cached component is matched by no-follow `fstatat` device/inode/type+mode from its **already checked parent**, before AND after each read. Changed cached identities are refused (then cleared on failed prevalidation), not reused as path authority. The actual leaf is opened RDONLY/NOFOLLOW/NONBLOCK/CLOEXEC, checked regular via its descriptor and matched against its no-follow current name after reading. Root identity is checked around each read. Deep paths retain metadata and do two bounded-FD descriptor walks; cache size never grows with depth/entry count. At most 33 persistent descriptors (root+32), up to two transient descriptors during deep walks.
- Discovery reuses its existing canonical entry result for dedup AND confined opening: no duplicate canonicalization and no per-file root acquisition. Both controlled/uncontrolled entrypoints use the same implementation; controls never substitute a different security/read path. A final root check also binds EMPTY/unsupported-only inventories to the acquired root. Traversal/glob/include/exclude/default-ignore/Git/case-collision/alias/language/diagnostic policies and total/file bounds remain. Every accepted source is really read and BLAKE3-hashed before returning; no cached text/hash/metadata-only freshness.
- Windows factors the existing source root acquisition and handle-relative cap-std opener, retaining one capability without SHARE_DELETE. Existing reparse/device/stream restrictions remain. No new DACL/library claim, Windows crate search or runtime environment; derived-data support is still refused. Native macOS source mode0755 AND real Everyone-ALLOW source fixtures work, while the same ACL fixture is refused by DirectoryAnchor without changing ACLs/modes. Source access and private derived placement are deliberately distinct policies.
- Initial canonical-root/ancestor acquisition is still trusted. Pre/post identity checks do NOT establish an atomic snapshot or exclude arbitrary ABA or concurrent writes after the last observation; no same-UID/administrator isolation claim. ## Current Darwin ACL policy and proof boundary

`src/placement_acl.rs` uses the existing independently published **exacl =0.13.0**, Darwin-only, default features disabled, MIT, MSRV 1.85. Its packaged changelog records maintained release 2026-05-05 and native macOS CI updates. Reviewed `lib.rs`, `acl.rs`, `aclentry.rs`, `qualifier.rs`, `util_macos.rs`, `util_common.rs`, `build.rs`, packaged license/changelog: public APIs accept typed borrowed paths/owned entries, synchronous CString/native ACL lifetimes are internal, returned ACL allocation is freed by Drop; no first-party unsafe, raw-pointer call, vendored fork or custom FFI. The optional bindgen/serde features are NOT enabled. Only the owned crate manifest was edited; Cargo automatically resolves lock changes, with parent retaining reconciliation/audit ownership. This source review is not a claim of a formal independent upstream audit.

The safe API is **path-based**, not `acl_get_fd`. The placement policy therefore establishes name stability from `/` downward BEFORE each descendant ACL query:

1. Open each real directory with NOFOLLOW; require trusted owner (current euid/root), reject non-sticky foreign-writable modes, then inspect ACL before opening/creating descendants. Reject **every extended ALLOW** (including inherited/inherit-only/current-owner entries) and unknown tags; conservatively do not infer principal/group membership, ACE ordering or effective-right subsets. Empty and deny-only ACLs cannot add foreign rights.
2. Non-sticky accepted parents have neither foreign write mode nor ACL grants. Trusted-owner sticky parents protect each already-checked trusted-owned child name: local Darwin `unlink(2)` and `rename(2)` document EPERM when neither directory nor child belongs to the caller; foreign-owned children fail ownership checks before their ACL query. This is the explicit sticky-name-stability premise, not a claim all entries of a sticky directory are immutable. An ancestor's own ACL is checked before trusting its child names. Root/current euid and mount administrators remain trusted. A hostile same-UID process is NOT isolated.
3. Opened object identity and no-symlink metadata are matched before/after the ACL query. These comparisons detect trusted accidental replacement; they are NOT the reason an attacker cannot race an insecure parent. The root-down owner/mode/ACL premise is necessary. On subsequent `validate/create_new/open_existing`, safe rustix F_GETPATH supplies the current name (including after an accidental rename), the **whole chain is revalidated root-down**, and final dev/inode must match the held descriptor. F_GETPATH alone proves nothing about parent stability.
4. mkdirat(0700)/exclusive openat(0600) happen only below validated parents. Inherit-only ALLOW parents are refused **before child creation**. Actual file type/euid/nlink/mode and Darwin ACL are checked before returning a writable handle. Existing directories/files never have modes or ACLs stripped/repaired/adopted by these APIs. An empty newly-created file can remain after a trusted concurrent policy change causes refusal; it contains no derived secret bytes.

Two native investigation results prevent unsafe shortcuts: `fgetxattr(fd, "com.apple.system.Security")` returned EPERM on a real hostile ACL fixture; `exacl::getfacl("/dev/fd/N")` returned fdescfs's empty ACL while the held file had Everyone ALLOW. The latter is retained as a native regression, **not** used in production. No `/dev/fd`/`/proc/self/fd` SQLite binding claim is made. Windows still fails before I/O; the prior bounded Windows-candidate review does not establish that no suitable library exists.

Native `tests/macos_acl.rs` covers explicit Everyone read/write/search/delete-child/write-security under mode0700, ancestor replacement rights, actual inherited and inherit-only ALLOW entries (verified via the native API), post-acquisition inheritance refusal before file creation, a mode0600 existing-file ALLOW refused without truncation/ACL edits, harmless inherited deny-only defaults preserved and usable, and the invalid `/dev/fd` shortcut. Privileged/actual foreign-UID attack execution and broader concurrent stress remain separate acceptance gates; the fixtures install real ACLs, not fabricated metadata or a claim of hostile same-UID isolation.

The actual root descriptor used for traversal is retained during each stamp read; parent metadata comes from actual opened directory descriptors. Device/inode/size/mtime/ctime are captured around the actual bounded hash read; file, parents and root are reopened/rechecked before returning. Source/parent/root changes around the read yield SOURCE_CHANGED or a confinement/read error. This is source inventory evidence only: callers still own Git HEAD, parser/grammar/version, external-config/semantic-input and committed-generation checks.

A filesystem type/name, nonzero nanosecond fields or one observed rapid edit does not prove coherency, timestamp uniqueness, ctime behavior, or network-cache semantics. Unknown/coarse/network filesystems have no bypass: the implemented code always hashes or errors. ## READY: shared byte reader for parent and transports

`kortex_repo::read_confined_bytes(root: &Path, relative: &str, max: u64) -> kortex_core::Result<Vec<u8>>` is implemented. Transport can replace `read_confined(...).into_bytes()` with this API for PNG/WOFF2 and other explicitly allowed asset types. It does not impose a MIME/extension policy; consumers must keep their own bounded allowlist/total-byte/entry policies.

- Same component validation, canonical root confinement, Unix rustix descriptor walk and real Windows cap-std/cap-fs-ext handle-relative resolver. No ambient `File::open` fallback. Nonregular files are refused from the actual opened descriptor before reading; Unix NONBLOCK refuses FIFOs without waiting for writers.
- Shared `confined::read_bytes` uses `take(max.saturating_add(1))`, returning `FILE_TOO_LARGE` for the lookahead byte. `u64::MAX` does not overflow. Bytes are not preallocated from untrusted metadata or the maximum.

- Added real binary/all-byte-values, exact/+1/zero/u64::MAX, empty, multibyte UTF-8 and invalid UTF-8 tests, 256 traversal depths, deterministic post-resolution leaf/parent symlink swaps, internal/external aliases and FIFO refusal. ## Storage-owner coordination: privacy and placement work in progress

Do not treat Windows confined source reads as private derived-data storage. `owner()` currently ignores non-Unix ownership, and Unix modes do not enforce a Windows DACL. No acceptable safe ACL implementation or runtime ACL evidence has yet been established. Storage must fail closed before creating directories, DB/sidecars/lock/marker/registry/model-cache files on unsupported privacy platforms; no chmod-equivalence claim.

A 0700 `.kortex` child under a non-sticky group/world-writable parent can be renamed/replaced by a different user with parent write+search permission. SQLite NOFOLLOW protects only its final leaf, not that parent.

Exact additive repo API now available for storage-owner review/integration:

- `kortex_repo::placement::require_derived_data_support() -> Result<()>`: **Windows/non-Unix returns `PRIVATE_STORAGE_UNSUPPORTED`, exit 8, before any filesystem I/O.** Storage should gate every derived-data path (Store read/write, directory creation, writer lock, repair, registry, cache) before side effects. Source reads remain supported and unchanged on Windows. Storage may implement an equivalent crate-local gate rather than depending on repo; do not duplicate a claim that modes enforce DACL privacy.
- `placement::DirectoryAnchor::acquire(path: &Path, create: bool) -> Result<DirectoryAnchor>`: Unix no-follow descriptor walk from `/`; requires absolute normal spelling, trusted UID (current effective UID or root) for every actual opened ancestor, denies non-sticky group/world-writable ancestors, permits sticky intermediates with trusted owners, requires final directory current-owner/no group/world bits. Missing directories are mkdirat(0700) only when create=true; existing directories never chmodded/adopted. Use canonical cache/root spelling, not a mutable alias whose earlier canonicalization hides insecure original components.
- `DirectoryAnchor::create_new(&self, name: &str) -> Result<std::fs::File>`: single-component, descriptor-relative exclusive no-follow 0600 creation; actual opened metadata must be regular, current-owner, nlink=1, no group/world access **before the writable handle is returned**. No truncation/adoption of existing artifacts. No SQLite VFS supplied.

These helpers implement a **Unix discretionary-mode placement policy**, not complete POSIX/macOS ACL enforcement. They trust root/current UID and the filesystem/mount administrator; ACL/capability/network-filesystem deployments require further review. They do not claim protection against a malicious same-user process. Held directory operations stay on the original identity after accidental rename; Unix descriptors do not prevent rename, and ambient SQLite/repair paths are not made handle-bound simply by retaining this anchor. No repeated check-then-open race-elimination claim. Storage owns call sites and end-to-end refusal tests; until integrated, these helpers do not change storage behavior. Sticky temporary directories remain supported.

## ACL API investigation: precise blocker, no dependency adopted

The earlier recorded candidates were rechecked against their actual downloaded source. A newly reviewed maintained candidate still does not supply Windows privacy:

- `winsafe 0.0.29`: reviewed source has safe `HFILE::CreateFile`, `CreateDirectory`, `HACCESSTOKEN::GetTokenInformation` and `InitializeSecurityDescriptor`, but no `GetSecurityInfo`/`GetNamedSecurityInfo`/protected-DACL construction wrappers sufficient for validation and owner-only creation. - **New candidate `fs-mistrust 0.16.1`**, Tor/Arti, MIT OR Apache-2.0, Rust 1.92: obtained for source review only with `cargo info fs-mistrust@0.16.1`, not added as a dependency. Commands `cargo search fs-mistrust --limit 3`, `cargo search windows-permissions --limit 5`, `cargo search win32-security --limit 5` retrieved public package metadata only. Production Windows privacy remains **unsupported**, not a chmod-based approximation. Need a maintained/reviewed safe owned SID/security-descriptor/token/handle interface, DACL validation, explicit inheritance protection, owner-only creation attributes applied before writes, and real runtime validation before lifting the capability gate.
