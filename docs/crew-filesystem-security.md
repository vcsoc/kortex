Reviewed `lib.rs`, `acl.rs`, `aclentry.rs`, `qualifier.rs`, `util_macos.rs`, `util_common.rs`, `build.rs`, packaged license/changelog: public APIs accept typed borrowed paths/owned entries, synchronous CString/native ACL lifetimes are internal, returned ACL allocation is freed by Drop; no first-party unsafe, raw-pointer call, vendored fork or custom FFI. The optional bindgen/serde features are NOT enabled. Only the owned crate manifest was edited; Cargo automatically resolves lock changes, with parent retaining reconciliation/audit ownership. This source review is not a claim of a formal independent upstream audit.

The safe API is **path-based**, not `acl_get_fd`. The placement policy therefore establishes name stability from `/` downward BEFORE each descendant ACL query:

1. Open each real directory with NOFOLLOW; require trusted owner (current euid/root), reject non-sticky foreign-writable modes, then inspect ACL before opening/creating descendants. Reject **every extended ALLOW** (including inherited/inherit-only/current-owner entries) and unknown tags; conservatively do not infer principal/group membership, ACE ordering or effective-right subsets. Empty and deny-only ACLs cannot add foreign rights.
2. Non-sticky accepted parents have neither foreign write mode nor ACL grants. Trusted-owner sticky parents protect each already-checked trusted-owned child name: local Darwin `unlink(2)` and `rename(2)` document EPERM when neither directory nor child belongs to the caller; foreign-owned children fail ownership checks before their ACL query. This is the explicit sticky-name-stability premise, not a claim all entries of a sticky directory are immutable. An ancestor's own ACL is checked before trusting its child names. Root/current euid and mount administrators remain trusted. A hostile same-UID process is NOT isolated.
3. Opened object identity and no-symlink metadata are matched before/after the ACL query. These comparisons detect trusted accidental replacement; they are NOT the reason an attacker cannot race an insecure parent. The root-down owner/mode/ACL premise is necessary. On subsequent `validate/create_new/open_existing`, safe rustix F_GETPATH supplies the current name (including after an accidental rename), the **whole chain is revalidated root-down**, and final dev/inode must match the held descriptor. F_GETPATH alone proves nothing about parent stability.
4. mkdirat(0700)/exclusive openat(0600) happen only below validated parents. Inherit-only ALLOW parents are refused **before child creation**. Actual file type/euid/nlink/mode and Darwin ACL are checked before returning a writable handle. Existing directories/files never have modes or ACLs stripped/repaired/adopted by these APIs. An empty newly-created file can remain after a trusted concurrent policy change causes refusal; it contains no derived secret bytes.

Two native investigation results prevent unsafe shortcuts: `fgetxattr(fd, "com.apple.system.Security")` returned EPERM on a real hostile ACL fixture; `exacl::getfacl("/dev/fd/N")` returned fdescfs's empty ACL while the held file had Everyone ALLOW. The latter is retained as a native regression, **not** used in production. No `/dev/fd`/`/proc/self/fd` SQLite binding claim is made. Windows still fails before I/O; the prior bounded Windows-candidate review does not establish that no suitable library exists.

Native `tests/macos_acl.rs` covers explicit Everyone read/write/search/delete-child/write-security under mode0700, ancestor replacement rights, actual inherited and inherit-only ALLOW entries (verified via the native API), post-acquisition inheritance refusal before file creation, a mode0600 existing-file ALLOW refused without truncation/ACL edits, harmless inherited deny-only defaults preserved and usable, and the invalid `/dev/fd` shortcut. Privileged/actual foreign-UID attack execution and broader concurrent stress remain separate acceptance gates; the fixtures install real ACLs, not fabricated metadata or a claim of hostile same-UID isolation.

All errors (including `SOURCE_CHANGED`, `SOURCE_STAMP_UNCERTAIN`, cancellation, unreadability) are NOT fresh results.

The actual root descriptor used for traversal is retained during each stamp read; parent metadata comes from actual opened directory descriptors. Device/inode/size/mtime/ctime are captured around the actual bounded hash read; file, parents and root are reopened/rechecked before returning. Source/parent/root changes around the read yield SOURCE_CHANGED or a confinement/read error. Stamps bind canonical root spelling, requested relative path, resolved relative path, actual root/parent/file identities and content hash. Initial root acquisition/ancestors remain the source-reader trust boundary. Before/after timestamps do NOT prove an atomic filesystem snapshot or exclude ABA races on arbitrary filesystems.

Inventory capture intentionally does an eager discovery/hash pass plus stamped rereads, then checks resolution/ignore/manifest inputs again. It binds effective serialized config, root identity even for EMPTY inventories, source identities/hashes, and bounded reads of relevant root/nested manifests/ignore files (without lossy Unix-backslash normalization). Directory-alias manifest coverage is not yet proved: `follow_symlinks=true` returns explicit SOURCE_STAMP_UNCERTAIN from this experimental inventory API, while ordinary controlled eager discovery remains supported. Truncated/failed source diagnostics return uncertainty, not fresh. Root/nested ignore/manifest/new/deleted-file changes are observed by hashing and inventory reconciliation, not directory-mtime guesses. This is source inventory evidence only: callers still own Git HEAD, parser/grammar/version, external-config/semantic-input and committed-generation checks.

**Metadata-only reuse is NOT justified or approved**, even for native APFS. A filesystem type/name, nonzero nanosecond fields or one observed rapid edit does not prove coherency, timestamp uniqueness, ctime behavior, or network-cache semantics. Unknown/coarse/network filesystems have no bypass: the implemented code always hashes or errors. Actual coarse/network mounts were not available/tested; no platform acceptance or snapshot-coherency claim is made for them. A later optimization needs parent review of the exact FS/identity/clock/change model and real mount evidence; it must not quietly enable an mtime heuristic.

Native regressions include restored-mtime/same-size source and manifest edits; 64 rapid source edits with actual rehashes; equal-byte atomic replacement; moved-back original inode under a replaced parent; deterministic leaf/parent/root/write mutations after a real hash read; empty/nonempty root replacement; new/delete/root and nested ignore/manifests; supplied-config changes; truncated inventory uncertainty; literal-backslash input identities; unproved directory-alias uncertainty; cancellation after actual reads; confinement/size/text-error preservation. There is no fabricated coarse/network runtime fixture.

## Storage-owner coordination: privacy and placement work in progress

Do not treat Windows confined source reads as private derived-data storage. `owner()` currently ignores non-Unix ownership, and Unix modes do not enforce a Windows DACL. No acceptable safe ACL implementation or runtime ACL evidence has yet been established. Storage must fail closed before creating directories, DB/sidecars/lock/marker/registry/model-cache files on unsupported privacy platforms; no chmod-equivalence claim.

A 0700 `.kortex` child under a non-sticky group/world-writable parent can be renamed/replaced by a different user with parent write+search permission. SQLite NOFOLLOW protects only its final leaf, not that parent.

Exact additive repo API now available for storage-owner review/integration:

- `kortex_repo::placement::require_derived_data_support() -> Result<()>`: **Windows/non-Unix returns `PRIVATE_STORAGE_UNSUPPORTED`, exit 8, before any filesystem I/O.** Storage should gate every derived-data path (Store read/write, directory creation, writer lock, repair, registry, cache) before side effects. Source reads remain supported and unchanged on Windows. Storage may implement an equivalent crate-local gate rather than depending on repo; do not duplicate a claim that modes enforce DACL privacy.
- `placement::DirectoryAnchor::acquire(path: &Path, create: bool) -> Result<DirectoryAnchor>`: Unix no-follow descriptor walk from `/`; requires absolute normal spelling, trusted UID (current effective UID or root) for every actual opened ancestor, denies non-sticky group/world-writable ancestors, permits sticky intermediates with trusted owners, requires final directory current-owner/no group/world bits. Missing directories are mkdirat(0700) only when create=true; existing directories never chmodded/adopted. Use canonical cache/root spelling, not a mutable alias whose earlier canonicalization hides insecure original components.
- `DirectoryAnchor::create_new(&self, name: &str) -> Result<std::fs::File>`: single-component, descriptor-relative exclusive no-follow 0600 creation; actual opened metadata must be regular, current-owner, nlink=1, no group/world access **before the writable handle is returned**. No truncation/adoption of existing artifacts. No SQLite VFS supplied.

These helpers implement a **Unix discretionary-mode placement policy**, not complete POSIX/macOS ACL enforcement. They trust root/current UID and the filesystem/mount administrator; ACL/capability/network-filesystem deployments require further review. They do not claim protection against a malicious same-user process. Held directory operations stay on the original identity after accidental rename; Unix descriptors do not prevent rename, and ambient SQLite/repair paths are not made handle-bound simply by retaining this anchor. No repeated check-then-open race-elimination claim. Storage owns call sites and end-to-end refusal tests; until integrated, these helpers do not change storage behavior. Sticky temporary directories remain supported.
